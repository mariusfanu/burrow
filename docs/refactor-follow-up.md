# Burrow code review and implementation plan

12 November 2026 · Baseline `acb605a` on `main` · Handoff to Sol 6.1

## Implementation order

| Priority | Work | Acceptance condition |
| --- | --- | --- |
| P1 | 1. Uninstall input, plan validation and removal mode | The CLI can receive an approval only for the current, verified plan and the removal mode shown in Burrow |
| P1 | 2. Selection menu verification | A same-count selection swap or a changed path cannot reach the confirmation key |
| P1 | 3. Bind a review to its CLI | Changing the CLI invalidates work that would otherwise apply a review to a different executable |
| P2 | 4. File and report consistency | Scans and reports stay current, Trash outcomes stay accurate, and settings edits preserve external changes |
| P2 | 5. PTY descriptor inheritance | A child has the controlling terminal it needs and cannot inherit unrelated app descriptors |
| P2 | 6. Run Log, treemap and accessibility | Live follow, zoom origins and keyboard access work throughout the supported window sizes |
| P2 | 7. Status stream and process boundaries | Samples and exit are handled in order, and malformed data and slow consumers have defined outcomes |
| P2 | 8. Disk Explorer performance | A measured improvement preserves protection decisions and cancellation |
| P2 | 9. Repeatable builds and tests | A fresh checkout can verify the package, generated app target and local bundle on macOS 26 |
| P3 | 10. Focused organization and cleanup | Moves and deduplication make the changed code easier to navigate without adding another abstraction layer |

Start with the failing fixture for each P1, then implement and run its focused suite. Keep changes independently reviewable. Within the P2 work, fix pipe delivery completion in step 7 before depending on complete output for the Clean sidecar or the Status retry logic. Preserve the macOS 26 deployment target and the Swift 6.2 package tools requirement. Use a disposable home, CLI script and fixtures for destructive-path tests. Each script should record arguments or confirmation bytes and write only in the fixture directory. Consult the earlier refactor before changing an existing boundary. ## 1. Verify Uninstall at the point of approval

**Finding.** `RunController.raisePrompt` checks the plan only for `.confirm`, after a 300 ms delay. `RunPanel` passes the terminal directly to `TerminalCanvas`, whose key and paste paths write to the child immediately. Disposable PTY probes confirmed that early raw Return and native Yes on an alternate `[y/N]` prompt reached the child with zero validator calls. A separate probe confirmed that `UninstallPlan.appPaths` can silently skip an incomplete extra app block. The Mole 1.70.0 confirmation loop accepts Return and `y`, and its personal-data selection can produce a new review. [RunController.swift](../Sources/Burrow/Run/RunController.swift#L355), [TerminalCanvas.swift](../Sources/Burrow/Run/Terminal/TerminalCanvas.swift#L180), [UninstallPlan.swift](../Sources/BurrowCore/Parsing/UninstallPlan.swift#L8), [Mole 1.70.0 confirmation loop](https://github.com/tw93/Mole/blob/V1.70.0/lib/uninstall/batch.sh#L2293-L2359)

1. Make guarded Uninstall runs expose Terminal output as read-only. Route keyboard and Paste through a controller-owned input decision, including the debug input path. Keep Select All, Copy, and native cancellation available. Keep typed password and terminal-protocol replies on their separate routes. If a personal-data picker is later exposed inside Burrow, explicitly model the picker and require a fresh verification on return. The existing Include Personal Data option already supplies the supported native selection path.
2. Represent validation against a particular terminal and prompt request. At native approval, require a running, uncancelled session, a matching prompt request, the expected supported prompt kind and the current complete plan. Re-read Preview Mode and the current prompt before writing the approval byte. A stale sheet or an unrecognized approval prompt must leave the command unconfirmed. Preserve a clear cancel path and the existing mismatch message. Keep the explicit confirmation action for permanent removal.
3. Parse the latest plan block into complete per-app records. Respect section boundaries and the checked CLI's indentation and path formatting. Compare both count and exact paths against the selected apps and check the count in a recognized `Remove N app(s)` prompt. Treat missing paths, malformed or extra app records, and duplicate primary paths as a mismatch. Feed this check from the current plan text so a presentation filter or log trimming cannot silently discard a record. Keep `UninstallTargeting`'s existing ambiguity handling for safe positional names.
4. Make the uninstall launch own its deletion mode and its positional arguments. In the installed Mole 1.71.0 script, an inherited `MOLE_DELETE_MODE=permanent` survives the default and `--permanent` is a recognized flag even if an app name supplied it. Build the uninstall child environment with `MOLE_DELETE_MODE=trash`, and let the explicit permanent option set `--permanent` for a live run. Filter empty and dash-prefixed target candidates at the targeting boundary. If an app has no usable positional spelling, surface an error before spawn. Use the positional syntax supported by the CLI. Verify argument and environment handling for the checked 1.70.0 version and the installed 1.71.0 version before updating compatibility claims. [UninstallModel.swift](../Sources/Burrow/Features/Uninstall/UninstallModel.swift#L293), [UninstallTargeting.swift](../Sources/BurrowCore/Parsing/UninstallTargeting.swift#L30), [CLILocator.swift](../Sources/BurrowCore/CLI/CLILocator.swift#L26)

**Verify.** Extend `DestructiveConfirmationTests`, `RunControllerTests` and the core plan/targeting tests. Cover immediate Return, keypad Enter, `y` and pasted input during the debounce, a changed yes/no prompt, a stale approval from a replaced prompt/session, a correct app followed by an incomplete extra block, duplicated paths, and a valid plan confirmed exactly once. Use a fixture that records the environment and argv for Trash, Preview and explicitly permanent launches. Include names `--permanent`, `--with-data`, and an app with a safe alternative spelling. Check password handoff with a fake echo-disabled reader and no real credential. In the app, verify that Terminal still displays and copies output during the run.

## 2. Verify exact selection in Mole menus

**Finding.** The driver reads the initial selection, visits rows it thinks need attention, and decides whether to toggle from the initial `preselected` bit. The final selected count can still match after a repaint swaps two marks. In an optimized disposable PTY fixture, `select([A])` succeeded and the fixture printed `CONFIRMED:B`. Purge also captures a focused path when reading a row and verifies only row text when applying, so equal or truncated labels can hide a changed path. [MenuDriver.swift](../Sources/BurrowCore/CLI/MenuDriver.swift#L121), [MenuFlowModel.swift](../Sources/Burrow/Features/Menus/MenuFlowModel.swift#L156)

1. Before each Space, verify the live position, row text and current selected state. Where a path was shown in the review, require the exact live focused path and fail on an ambiguous or stale read. Check the same row and the expected mark after the toggle. Retain the cursor walk and cancellation checks across pages.
2. Prove every desired row is actually marked and reconcile the desired set with the CLI's total selection count and list shape. Visit previously selected rows that need clearing. If the protocol cannot resolve unexpected marks or establish the exact selected set, stop with the existing retry/rescan path. Put final verification and Enter on one driver path. Check cancellation and the latest Preview Mode at the handoff. If an additional CLI confirmation follows, preserve the native prompt flow.
3. Reject invalid selection indices, duplicates and invalid CLI-reported row counts as verification errors. Avoid reserving unbounded storage from the header. Reject a changed menu or process during the final check.

**Verify.** Extend the paged fake menu in `CLIIntegrationTests`. Capture actual confirmation bytes and identities. Cover a same-count A/B swap after initial read, identical row labels with changed focused paths, preselected rows on another page, duplicate indices, impossible counts, partial repaints and cancellation between applying marks and confirmation. Keep a successful paged selection fixture and preserve the no-menu Preview behavior for the flows that list only.

## 3. Invalidate reviews when the CLI changes

**Finding.** Settings can publish a new `CLIInfo` while app-owned feature models survive. A two-CLI fixture completed a Clean review on A, then used that review to launch a live command on B. Optimize plans and Uninstall inventory have the same ownership concern. Menu flows hold a live PTY for A while the app can show B as the chosen CLI. [AppModel.swift](../Sources/Burrow/App/AppModel.swift#L202), [AppModel+Actions.swift](../Sources/Burrow/App/AppModel%2BActions.swift#L6), [CleanModel.swift](../Sources/Burrow/Features/Clean/CleanModel.swift#L68), [PageHost.swift](../Sources/Burrow/App/Root/PageHost.swift#L21)

1. Validate an explicitly chosen candidate before persisting it. In the existing app coordination code, handle a change in accepted CLI identity explicitly. Invalidate open confirmations and review inputs before publishing the replacement. Cancel or invalidate read-only work from the old source with the features' existing ownership tokens. Require a fresh Clean/Optimize review and Uninstall inventory. End a menu selection waiting on the old child and require a rescan. Clear CLI-dependent Disk Explorer and History data. Keep the active run's identity and result tied to its original CLI. If changing CLI while it is mutating cannot be presented coherently, defer the replacement until that run finishes.
2. At the action boundary check the review's source and ownership again so a stale button or alert closure cannot launch a different CLI. Prefer using the existing `CLIInfo` identity as the first comparison and one app coordination method over a generic feature lifecycle. Use a separate plan if stronger executable identity across in-place replacement is needed.
3. Audit `CLILocator.isSafeToRun` separately for the custom executable trust promise. It stats only the resolved leaf and later launches by path. A replaceable parent directory or symlink and a wrapper that delegates to an untrusted tree deserve a fixture before changing the rules. Establish the accepted Homebrew, user install and custom paths. Check actual ancestor permissions, ownership and symlink replacement behavior, including sticky directories. Revalidate a resolved executable at launch where practical and document the remaining trust in the chosen Mole installation. Preserve the existing system-first `PATH`. [CLILocator.swift](../Sources/BurrowCore/CLI/CLILocator.swift#L53)

**Verify.** Use two executable fixtures and injected command gates. Complete A's review, switch to B, then invoke the stale action and assert neither CLI received the stale approval. Repeat with Clean's external-volume question, Optimize, Uninstall and a live menu scan. Deliver late A output after B's inventory is ready. Confirm a failed custom selection that leaves the effective CLI unchanged and a successful B rescan behave coherently. Cover settings and main window entry points.

## 4. Correct file and report ownership

- **Invalidate in-flight scans as well as the cache.** `markStale()` clears the cache but a scan that started before it can write back. Reproduce by opening B, leaving Analyze, invalidating, delivering the old B result, returning to trigger a B refresh, then navigating to C and back before the B refresh completes. The old B can be served from cache. Associate results with a filesystem revision or invalidate the existing load token on external mutation. A refresh clears staleness when a current result is accepted. Disable mutations against known-stale entries while preserving loading, Cancel, Back and Rescan. Test late success and error, cancelled refresh, navigation back, and cache reuse for an unchanged folder. [AnalyzeModel.swift](../Sources/Burrow/Features/Analyze/AnalyzeModel.swift#L96)
- **Distinguish missing, moved and failed paths.** `TrashMover` treats ENOENT as intentionally unlogged, but the model counts every outcome with a nil error as moved. Make outcome state explicit and retain any restore URL on a move. Remove missing rows from the presentation and reconcile selection. Count and announce only actual moves, only register Undo for verified moves, and invalidate other features only when something changed. Keep partial failure, log-write failure and retry behavior. Test all-missing, mixed moved/missing/failed and restore after mixed results with `TrashClient`. [TrashMover.swift](../Sources/BurrowCore/Safety/TrashMover.swift#L129), [AnalyzeModel.swift](../Sources/Burrow/Features/Analyze/AnalyzeModel.swift#L298)
- **Tie Clean details to the current run.** A fake CLI emitted a fresh summary and left an old `clean-list.txt` on disk. The review attached the old path. Compare pre-run file identity/freshness with the result and require Mole's current-run detail announcement before accepting the file. Prefer a per-run destination if the supported CLI exposes one. With a shared file, keep the summary and report unavailable details if ownership is ambiguous. Read the existing sidecar in place. Test no announcement, unchanged file, a fresh announced file, failed/cancelled previews and replacement during read. [CleanModel.swift](../Sources/Burrow/Features/Clean/CleanModel.swift#L87), [CleanPreviewStream.swift](../Sources/Burrow/Features/Clean/CleanPreviewStream.swift#L36)
- **Preserve linked settings files and external edits.** A temporary-home test showed that saving a valid final symlink atomically replaced the symlink and left the dotfiles target unchanged. Make `ConfigFile` update the verified existing target atomically while preserving the link. Report an actionable error if the target cannot be verified. Keep support for linked parent directories and unreadable/dangling-file refusal. A separate fixture reproduced a Maintenance toggle overwriting an edit made since load. Apply a single toggle against the latest on-disk set in `OptimizeWhitelistStore`. For the Purge sheet's whole-list Save, detect a changed source and offer reload while preserving the draft. Check for change immediately before write because other processes can edit the file independently. Test relative and absolute final symlinks, legacy fallback, malformed data and out-of-band edits. [ConfigFile.swift](../Sources/BurrowCore/Config/ConfigFile.swift#L29), [MaintenanceSettingsModel.swift](../Sources/Burrow/Features/Settings/MaintenanceSettingsModel.swift#L27), [PurgePathsSheet.swift](../Sources/Burrow/Features/Menus/PurgePathsSheet.swift#L51)

## 5. Prevent PTY descriptor inheritance

**Finding.** The `forkpty` child closes descriptors 3 through 1023. A standalone probe duplicated `/dev/null` to fd 1200 and launched itself through both spawners. The PTY child inherited fd 1200. The piped child using `POSIX_SPAWN_CLOEXEC_DEFAULT` had fd 1200 closed. [cpty.c](../Sources/CPTY/cpty.c#L25)

Add a fixture for fd 1200 (skip with a reason if the runner cannot open that descriptor). Use a supported Darwin close-on-exec or descriptor-closing approach that covers descriptors above 1023 and remains safe in the child between fork and exec. Check the deployment SDK before choosing the implementation. This host's open-file limit was 1,048,575, so benchmark startup if the solution uses a per-fd loop. Preserve `/dev/tty`, terminal size, the process group, EOF and `ChildExitWatcher` behavior. Verify child stdin/stdout/stderr, no leaked fd, resize, fast exit, write, cancellation and shutdown in the existing process and PTY suites.

A probe with 50/30/20 weights produced three different normalized rectangles for the middle tile at 1×1, 800×400, and 400×800. Share the stage's normalized rect for the current parent/child pair with list and keyboard open. Use a neutral origin for entries without a visible tile and preserve the back transition. Verify list, tile, keyboard, back and resize interactions, including Reduce Motion. [AnalyzeModel.swift](../Sources/Burrow/Features/Analyze/AnalyzeModel.swift#L143), [AnalyzeEntryList.swift](../Sources/Burrow/Features/Analyze/AnalyzeEntryList.swift#L35), [TreemapLayer.swift](../Sources/Burrow/Features/Analyze/Treemap/TreemapLayer.swift#L25)

## 7. Make streaming completion and format handling explicit

- **Status ordering, freshness and retries.** `StatusStore` creates separate main-actor tasks for parse errors and snapshots. The command continuation uses a single `Task.yield()` before accounting for failures. Use an ordered consumer for one command attempt and make the attempt finish after accepted events are drained. Keep existing stream/source ownership so rapid page, CLI and window-visibility changes discard old events. The dashboard currently labels the retained snapshot Live before the new source produces a sample. Derive freshness from current-source sample delivery, with a deadline based on the configured cadence and an injected clock. `StatusSnapshot` has optional fields throughout, so `{}` or an object of unknown keys can currently decode and appear live. Define a minimal shape from Mole fixtures that still accepts partial samples. Bound the size of an unterminated record and recover on the next newline. Test a final sample immediately before exit, a silent restart, a source that goes silent after a sample, malformed and partial records, an oversized unterminated line, and late data from a replaced stream. [StatusStore.swift](../Sources/Burrow/Features/Status/StatusStore.swift#L41), [StatusDashboard.swift](../Sources/Burrow/Features/Status/StatusDashboard.swift#L11), [NDJSONParser.swift](../Sources/BurrowCore/Parsing/NDJSONParser.swift#L23), [StatusSnapshot.swift](../Sources/BurrowCore/Models/StatusSnapshot.swift#L94)
- **Piped output and PTY backpressure.** A probe delayed a stdout callback for 2.5 s. The stream returned success at 1.0 s while the callback was still in progress. Distinguish a descendant holding a pipe open from a callback delivering bytes the reader already accepted. Quiesce accepted deliveries before successful return and make a drain cutoff an explicit incomplete-output outcome for callers expecting complete JSON or plans. Test a gated callback and a disposable descendant retaining a writer. Verify the return contract, reap and shutdown separately. Measure queued bytes and RSS with PTY output faster than the main actor can consume it. If needed, bound the transport with lossless backpressure. Dropping bytes would break escape sequences and menu verification. Keep GCD for descriptor readiness and the child-exit timer. [CommandRunner.swift](../Sources/BurrowCore/CLI/CommandRunner.swift#L66), [PTYSession.swift](../Sources/BurrowCore/CLI/PTYSession.swift), [CLITerminal.swift](../Sources/BurrowCore/CLI/CLITerminal.swift#L41)

## 8. Reduce repeated Disk Explorer protection work

**Measured candidate.** An optimized standalone fixture timed current `TrashGuard` classification for ordinary siblings in a disposable home with 40 irrelevant Group Containers and an OrbStack fixture. Three runs took 143–161 ms for 50 entries, 588–614 ms for 200, and 2.89–2.99 s for 1,000. `TrashRisk` on 1,000 entries took 15.9–16.7 ms. These are classification times. Analyze prepares this off the main actor, but its detached worker keeps going after the parent scan is cancelled. [TrashGuard.swift](../Sources/BurrowCore/Safety/TrashGuard.swift#L83), [AnalyzePresentation.swift](../Sources/Burrow/Features/Analyze/AnalyzePresentation.swift#L41), [AnalyzeModel.swift](../Sources/Burrow/Features/Analyze/AnalyzeModel.swift#L217)

1. Capture a Release baseline in a fixture that feeds the app valid Analyze JSON for 50, 200 and 1,000 sibling entries. Measure command-exit-to-presentation and cancellation lag. Preserve the current implementation as a comparison for classification parity.
2. Make a scan-scoped preparation context for repeated observations such as protected-root identities, the Group Containers directory listing and common ancestors. Limit it to one display snapshot. Keep live per-path validation for every actual move, using the same underlying protection rules. Check cancellation inside the preparation loop and propagate scan cancellation to the worker. Publish only when the load still owns the result.
3. Compare decisions for symlinks, protected ancestors, missing files, APFS aliases, iCloud and OrbStack. Compare alternating optimized runs on the same fixtures. Record median and spread. Keep the optimization only if the gain is repeatable and the scan and Trash fixtures agree.

Use native Instruments for secondary candidates. Capture SwiftUI update counts, main-thread time and responsiveness during 30,000- and 120,000-line logs with Terminal both open and closed, Status on/off-screen, and History loading its 200-session limit. Watch memory over repeated scans and page switches. Move decoding/presentation off the main actor or narrow view dependencies where those traces show a cost. The prior formatter, app-icon, Treemap selection and NDJSON compaction experiments already cover their original workloads. [Apple’s SwiftUI performance guide](https://developer.apple.com/documentation/xcode/understanding-and-improving-swiftui-performance.md), [prior measurements](simplification.md#how-to-measure)

## 10. Keep the feature layout and tighten boundaries as touched

The existing target split (`Burrow` / `BurrowCore` / `CPTY`), feature folders and synchronized Xcode source group fit the project. Preserve exhaustive `Screen` switches and feature-owned state. Keep app composition in `App/`, shared running UI and prompt handling in `Run/`, and protocol parsing and process mechanics in `BurrowCore/`.

- Extract the guarded approval policy and plan state from `RunController` if step 1 makes them a distinct responsibility. The controller should own the run lifecycle and expose narrow native approval and terminal-input entry points. Avoid a second representation of the live prompt and a generic run-state machine.
- If file navigation in `Run/` still gets in the way after these changes, make a move-only pass. `Run/Log/` can hold `RunLogList`, `LogRow`, `LogIcon`, `LogFollowState`, `LogViewport` and `HiddenLinesNote`. Put `TerminalCanvas`, `TerminalPanel` and `RunTerminalToggle` in `Run/Terminal/`. Group `CompletionHero`, `CompletionBanner`, `LandingRipple` and `RunController+Completion` in `Run/Completion/`. Keep the panel and controller at the `Run/` root and use the existing `Run/Prompts/` folder for prompt views. Regenerate the app project and build both entry points after the moves.
- Split Disk Explorer preparation from `AnalyzeModel` as part of step 8. Keep navigation, Trash, Undo and invalidation coordinated by the existing model. Group core Mole-specific parser, config and process files into subfolders only where ownership becomes clearer after these changes. Preserve public type names and SwiftPM target boundaries.
- Consolidate proven duplication and misplaced ownership. Share the tile/list origin computation and uninstall approval path. Move the shared Mole configuration line parser from `WhitelistStore` into `ConfigFile` when fixing the shared write behavior. Keep terminal screen and line assembly separate over the shared tokenizer. In touched code, favor native controls, stable model-owned identity, explicit observation dependencies, and checked isolation for pure Swift state. Keep narrow AppKit bridges for the terminal, window occlusion and About panel.
- Treat localization as a separate, scoped migration. `String`-backed model labels, notices and error text cannot be extracted like literal SwiftUI keys. Start with one screen and its model messages, retain verbatim CLI/user data, and verify pluralization, byte units and long translations before extending. Keep compatibility with macOS 26 when adopting newer SwiftUI APIs. A lint tool or new module should address a concrete maintenance problem before it becomes a repository-wide change.

## Baseline checks for this review

- Debug and release each reported 320 tests, nine host-only skips and one failed copy assertion, using Swift 6.4.2 on macOS 27.3. Package tests ran with temporary caches and the native SwiftPM backend because the managed shell blocked standard cache writes and SwiftPM's nested sandbox. The copy failure reproduced in a focused rerun. An independent `NSPasteboard.withUniqueName()` probe also returned `false` on `setString` in this shell.
- XcodeGen 2.46.0 generated the synchronized source group from a fresh archive. The unsigned Xcode app build attempt stopped during package resolution on denied cache writes. `bash -n` passed for the packaging scripts. Native UI, spoken VoiceOver, macOS 26 and notarized distribution remain open verification items.
